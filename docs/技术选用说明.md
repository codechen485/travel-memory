# 《行囊》技术选型说明

> 本文档记录每个技术选型的理由，方便面试时回答"为什么选这个技术"。

---

## 一、后端技术栈

### 1. NestJS（后端框架）

**选型理由：**
- **企业级架构**：内置模块化、依赖注入、装饰器模式，代码结构清晰，适合中大型项目
- **TypeScript 原生支持**：从底层就是为 TS 设计的，类型安全贯穿始终
- **生态成熟**：官方提供认证（Passport）、配置管理、定时任务、WebSocket 等模块，不需要自己造轮子
- **与前端统一语言**：前后端都是 TypeScript，降低认知成本

**面试回答要点：**
> "选 NestJS 是因为它提供了企业级的架构规范——模块化、依赖注入、统一的异常处理。相比 Express 需要自己搭架构，NestJS 开箱即用；相比 Spring Boot，它更轻量且与前端共享 TypeScript 技术栈，一个人全栈开发效率更高。"

**对比：**
| 框架 | 优势 | 劣势 |
|------|------|------|
| NestJS | 架构规范、TS 原生、模块化 | 学习曲线稍陡 |
| Express | 极简、灵活 | 需要自己搭架构，大项目容易混乱 |
| Spring Boot | 生态最成熟 | Java 生态重，与前端技术栈割裂 |
| Koa | 轻量、中间件机制好 | 生态不如 NestJS 完整 |

---

### 2. TypeScript（编程语言）

**选型理由：**
- **类型安全**：编译期发现错误，减少运行时 bug
- **开发体验**：IDE 自动补全、跳转定义、重构支持
- **全栈统一**：前后端同一门语言，降低切换成本

**面试回答要点：**
> "TypeScript 的类型系统能在编译期捕获大量错误，比如接口参数类型不对、返回值使用错误等。对于个人全栈项目，统一用 TS 可以大幅减少上下文切换的认知负担。"

---

### 3. Prisma（ORM）

**选型理由：**
- **类型安全**：根据 schema 自动生成 TypeScript 类型，查询结果有完整的类型提示
- **声明式 Schema**：`schema.prisma` 文件直观定义数据模型，比手写 SQL 或注解更清晰
- **迁移管理**：`prisma migrate` 自动生成 SQL 迁移文件，支持版本控制
- **Prisma Studio**：内置可视化数据浏览器，开发调试方便
- **多数据库支持**：切换数据库只需改一行配置

**面试回答要点：**
> "Prisma 的核心优势是类型安全——它的客户端是根据 schema 自动生成的，查询时字段名写错编译就会报错。相比 TypeORM 的装饰器方式，Prisma 的声明式 schema 更直观，而且 Prisma Studio 让开发阶段调试数据非常方便。"

**对比：**
| ORM | 优势 | 劣势 |
|-----|------|------|
| Prisma | 类型安全、schema 直观、Studio 工具 | 复杂查询性能略差 |
| TypeORM | 装饰器风格、功能全面 | 类型推导不如 Prisma |
| Sequelize | 老牌稳定 | API 老旧，TS 支持一般 |
| 手写 SQL | 性能最优 | 开发效率低、容易 SQL 注入 |

---

### 4. PostgreSQL（数据库）

**选型理由：**
- **功能强大**：支持 JSONB、全文检索、数组类型、CTE 递归查询，MVP 阶段不需要额外引入 Elasticsearch
- **数据一致性**：ACID 事务、严格的类型系统，比 MySQL 更可靠
- **扩展性好**：PostGIS 扩展支持地理数据（第二阶段地图功能可以直接用）
- **开源免费**：社区活跃，文档完善

**面试回答要点：**
> "选 PostgreSQL 主要考虑两点：一是它的功能比 MySQL 更丰富，JSONB 可以存半结构化数据，全文检索够用就不需要引入 Elasticsearch；二是第二阶段要做地图功能，PostGIS 扩展可以直接支持地理空间查询，不用额外搭服务。"

> ✅ 实际调整：地图功能最终做成**城市级足迹**（手输地名匹配 `china-places` 字典在前端 Leaflet 标点），未使用 PostGIS 地理空间查询，也未绘制 GPS 轨迹线。

**对比：**
| 数据库 | 优势 | 劣势 |
|--------|------|------|
| PostgreSQL | 功能全面、JSONB、PostGIS | 配置稍复杂 |
| MySQL | 普及度高、简单 | 功能不如 PG 丰富 |
| MongoDB | 灵活 schema | 事务支持弱，不适合关系型数据 |

---

### 5. Redis（缓存）

**选型理由：**
- **高性能缓存**：内存存储，读写速度远超数据库
- **轻量**：单线程模型，部署简单
- （预留能力）会话黑名单、接口限流——见下方“实际使用”

**面试回答要点：**
> "本项目 Redis 实际用作**只读接口的结果缓存**——个人统计（60s）和灵感漂流公开文案分页列表（30s），配合写操作主动失效。实现上对 ioredis 做了**优雅降级**封装：Redis 未部署或连不上时所有缓存方法安全短路、回落查库，接口绝不报错，所以本地开发不启 Redis 也能跑。JWT 黑名单、接口限流是 Redis 的常见用法，本项目采用无状态 JWT 未引入黑名单，暂不做限流。"

> ✅ 实际使用与原设想有出入：仅落地了结果缓存；JWT 黑名单/限流未实现。

---

### 6. Passport + JWT（认证方案）

**选型理由：**
- **无状态**：JWT 不需要服务端存 session，适合前后端分离架构
- **标准化**：JWT 是行业标准，前端存 localStorage/cookie 都行
- **Passport 生态**：策略模式，以后加微信登录、GitHub 登录只需加一个 Strategy
- **NestJS 原生集成**：`@nestjs/passport` 和 `@nestjs/jwt` 官方维护

**面试回答要点：**
> "选 JWT 是因为前后端分离架构下，无状态认证更合适——服务端不需要存 session，扩展性好。Passport 的策略模式让认证逻辑可插拔，以后如果要加第三方登录，只需要新增一个 Strategy 就行，不用改核心代码。"

---

### 7. bcrypt（密码加密）

**选型理由：**
- **抗暴力破解**：内置 work factor（成本因子），可以调节加密难度
- **行业标准**：最广泛使用的密码哈希算法之一
- **自动加盐**：不需要手动管理 salt

---

### 8. class-validator（参数校验）

**选型理由：**
- **装饰器声明式**：在 DTO 类上直接用 `@IsString()`、`@IsEmail()` 等装饰器定义规则
- **与 NestJS 深度集成**：配合 `ValidationPipe` 全局生效，自动返回校验错误
- **类型安全**：校验规则和 TypeScript 类型一致

---

## 二、前端技术栈

### 1. Vue 3（前端框架）

**选型理由：**
- **组合式 API**：逻辑复用比 Options API 更灵活，类似 React Hooks 但更简洁
- **响应式系统**：基于 Proxy 的响应式，性能优于 Vue 2 的 Object.defineProperty
- **学习曲线平缓**：模板语法直观，比 React 的 JSX 更容易上手
- **生态完善**：Vue Router、Pinia 都是官方维护

**面试回答要点：**
> "选 Vue 3 是因为组合式 API 让逻辑复用更灵活，同时保持了模板语法的直观性。相比 React，Vue 的响应式是自动的，不需要手动管理状态更新；相比 Angular，Vue 更轻量，学习成本更低。"

**对比：**
| 框架 | 优势 | 劣势 |
|------|------|------|
| Vue 3 | 易上手、响应式自动、组合式 API | 大型企业采用率不如 React |
| React | 生态最大、就业面广 | JSX 学习成本、需要手动管理状态 |
| Angular | 企业级、完整方案 | 过于笨重、学习曲线陡 |

---

### 2. Vite（构建工具）

**选型理由：**
- **极速启动**：基于 ESM 的按需编译，开发服务器启动是毫秒级
- **HMR 快**：热更新不随项目规模变慢
- **生产构建**：基于 Rollup，打包优化好
- **配置简单**：比 Webpack 配置量少很多

**面试回答要点：**
> "Vite 利用浏览器原生 ESM 支持，开发时不需要打包，按需编译请求的文件，所以启动速度是毫秒级的。Webpack 需要全量打包再启动，项目大了就很慢。"

---

### 3. Naive UI（组件库）

**选型理由：**
- **TypeScript 原生**：类型定义完善，IDE 提示好
- **主题定制灵活**：CSS 变量方式定制主题，比 Element Plus 的 Sass 变量更灵活
- **组件丰富**：覆盖常用场景，按需引入体积小
- **设计现代**：视觉风格比 Element Plus 更现代

**面试回答要点：**
> "从 Element Plus 换到 Naive UI 主要因为两点：一是 Naive UI 的 TypeScript 支持更好，类型推导更完善；二是它的主题系统基于 CSS 变量，定制起来更灵活，而且视觉风格更现代。"

---

### 4. Pinia（状态管理）

**选型理由：**
- **Vue 官方推荐**：已取代 Vuex 成为官方推荐的状态管理库
- **简洁 API**：没有 mutation，直接修改 state，支持 TypeScript 推导
- **模块化**：每个 store 独立定义，自动代码分割

**面试回答要点：**
> "Pinia 是 Vue 官方推荐的新一代状态管理库，相比 Vuex 去掉了 mutation 的概念，API 更简洁，而且对 TypeScript 的支持是原生的——store 的 state、getter、action 都有完整的类型推导。"

---

### 5. Axios（HTTP 客户端）

**选型理由：**
- **拦截器**：统一处理请求头（加 token）、响应错误（401 跳转登录）
- **自动 JSON 转换**：请求/响应自动序列化
- **取消请求**：支持 AbortController，组件卸载时取消未完成请求
- **比 fetch 好用**：fetch 不自动处理错误状态码（4xx/5xx 不 reject）

---

### 6. Tailwind CSS（样式方案）

**选型理由：**
- **原子化 CSS**：不用想类名，直接用 `flex items-center gap-2` 写样式
- **开发效率高**：不用在 CSS 文件和模板之间来回切换
- **体积小**：生产构建自动移除未使用的样式
- **响应式方便**：`md:flex-row sm:flex-col` 前缀搞定响应式

---

## 三、基础设施

### 1. Docker Compose（容器编排）

**选型理由：**
- **一键启动依赖**：`docker-compose up -d` 同时启动 PostgreSQL + Redis
- **环境一致**：开发、测试、生产环境用同样的配置，避免"我本地没问题"
- **隔离性**：数据库和缓存跑在容器里，不污染本地环境

**面试回答要点：**
> "用 Docker Compose 主要是为了环境一致性——数据库和缓存的版本、配置都写在 docker-compose.yml 里，团队成员拉下来直接 `docker-compose up` 就能跑，不会出现版本不一致的问题。"

## 四、AI 能力

### DeepSeek API（直调）

**选型理由：**
- **MVP 阶段够用**：直接调用 API 做场景识别和文案生成，不需要复杂的 RAG 架构
- **成本低**：按量计费，开发阶段花费很少
- **快速迭代**：不需要维护向量数据库和 embedding 模型

**面试回答要点：**
> "MVP 阶段直接调用 DeepSeek API 是最务实的选择——不需要引入向量数据库和 RAG 架构，快速验证产品价值。等用户量上来、需要更精准的知识检索时，再考虑引入 RAG（最终未引入）。实际用 `deepseek-flash` 多模态，把「看图识别场景 + 生成三风格文案」合并为单次调用，用 `response_format=json_object` 拿到结构化结果。"

## 五、整体架构思路

**为什么这样组合？**

```
前端：Vue 3 + Naive UI + Tailwind CSS
        ↓ Axios
后端：NestJS + Prisma + PostgreSQL + Redis
        ↓
AI：DeepSeek API（直调）
```

核心原则：
1. **全栈 TypeScript**：前后端同一门语言，降低认知负担
2. **MVP 优先**：只选必要的技术，不引入过度设计（不上 ES、MQ、对象存储）
3. **渐进式扩展**：第二阶段按需引入 RAG、地图、对象存储
4. **一个人能搞定**：技术栈不要太重，一个人能维护全套
